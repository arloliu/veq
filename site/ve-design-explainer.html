虛擬機台（VE）設計導讀

用白話與圖解說明：VE 是什麼、一台 VE 的內部怎麼運作、它怎麼從證據學出來，以及整個服務怎麼讓「上線一種新機型」越來越便宜。

依據 2026-10-10 晚間的設計狀態整理：決定紀錄 V-1～V-19；proposal P1 的 §8 變更已套用到 ve-architecture.md 與 ve-generation-service.md（P1 §1 的搬移除外）；GEM skeleton 已加入物件狀態機（ve-gem-skeleton.md §6）。設計仍在重新推導（V-4），細節以 docs/specs/ve/ 為準。

1. 先抓住三個重點

VE＝一群互相牽動的狀態機GEM 狀態機、每個模組一份、每個物件（carrier、job、晶圓）一份，彼此透過同步轉移牽動，共用一個變數庫（V-10）。
訓練＝分層 prior＋可替換的 learner標準與手冊提供骨架，log 提供真實行為與時間。學出來的東西要過兩種分數與升版 gate，才會成為正式版本。
服務本身也會學「用哪個 learner、哪組參數」也是有指標的假設，記在 experiment registry。目標是用更少的證據與人時上線新機型。

2. VE 是什麼、為什麼要做

EAP、FDC 這類 host 軟體要連真機才能測，但生產機台不能拿來試，錯誤情況也難製造。VE 是扮演機台的程式：站在 HSMS 被動端，送出和真機一樣的訊息、節奏，甚至一樣的「不合規」（quirk）。fab 裡機型很多，不可能一台一台手寫，所以真正要做的是一個從證據學出 VE 的服務。

pilot log 裡有三個對象：VE 模擬機台與它的 load-port controller；第三個（stream 99）標為 FDC 連線，暫不模擬（V-18）。

設計仍在重新推導：負責人在 2026-10-09 重開整個設計（V-4），pilot gate 與各種數字在 phase 2 重新決定。本頁說的是「目前的方向」，不是定案。

3. 全貌：兩層學習迴圈

divergence 先來自離線重播，也來自 host 測試回報；證據不足時服務產生資料需求給人。外層迴圈見第 10 節。

Profile：一種機型（鍵：model＋firmware 範圍）的行為說明書，版本不可修改，每條規則記錄層級與來源。runtime 載入 Profile、可選的 tool delta（學出來的單台差異）與 Instance Overlay（站點設定）。原則：skeleton 是程式，tool delta 是資料；Profile 只能透過 gate 升版（架構 §2、§3）。

4. 一台 VE 的內部

訊息各有位置：查詢讀變數庫；S6F11 是轉移的輸出，report 是當下的變數快照；host 指令先過 guard；製程進度是 Scenario 與時鐘驅動的自發轉移。要把事件拆到個別晶圓或腔體，需要 report 定義。

插槽是唯一能放非狀態機元件的地方（交錯選擇、值產生）：只能從 guard 允許的轉移裡挑、只能透過變數歷史寫值、狀態存在 Instance State，所以一樣能 checkpoint 與重播。其餘都是可檢查的狀態機。

物件狀態機

E87（carrier）、E40（process job）、E94（control job）、E90（substrate）與 E39（物件服務）是 skeleton 的可選能力：機台只有手冊宣告的那些，標準當 prior，手冊與 log 提供差異（V-10）。主標準定義物件、狀態模型與抽象服務，.1 標準把服務對到 SECS-II。

共通慣例：一個轉移一個 CE，同模型的所有物件共用，靠 report 裡的物件 ID 區分；標準不指定 CEID，所以 CEID 一律是機台資料。連鎖轉移會立刻接著走，但仍依序回報。

耦合規則：驗證把關（carrier 未驗證不啟動 PJ）、pooling 取代排隊（CJ 決定 PJ 順序）、終止往下傳（CJ 停止會傳到 PJ，反之不會）、消滅跟著料走。物件狀態會進 checkpoint；機台重啟、factory reset 時怎麼變仍待 phase 3。

5. 一條指令的旅程

guard 的結果有四種（架構 §3.2）：performed、accepted-pending（HCACK=4）、rejected、stalled（只用於 Scenario）。guard 看來源：host 指令受 LOCAL 模式限制，操作員動作不受。回覆之後還有依時間展開的狀態變化，所以 VE 不能只是查表回覆。

6. 證據與轉換器

pilot 樣本是同型號兩台蝕刻機一天的 EAP log（69 分鐘與 6 小時，P1 §1），看得出這種 log 的極限：

EAP log 給得出給不出
事件順序與頻率、回覆格式、host 查了哪些 IDreport 值對應哪個變數（定義在樣本開始前就送過）
EAP 端的記錄時間（0.1 ms）線上時間，以及連線、Select、T3 等傳輸事件
被接受的指令被拒的指令、連線建立（樣本裡都沒有）
一天內出現的事件罕見事件：第 4 小時事件種類還在增加；69 分鐘那份有 21% 測試事件的 ID 沒看過
—gateway 自己對機台的流量（某種 FDC 模式下會 polling、每分鐘 ping）

長期主要來源是 traffic log service：從 gateway 拿流量，打包成 captures 存進 fab 的物件儲存；它在自己的 repository，veq 只讀（V-12、V-14）。在那之前用轉換後的 EAP log，之後它仍是另一個觀察位置。證據來歷沿用 tracepack 欄位（V-7）：pack 的 capture_method、vantage，記錄的 fidelity；傳輸層與壞 frame 的證據一定要 wire-exact。

盲點宣告：每個 capture 都要宣告已知看不到的流量（例如 gateway 自己發給機台的訊息）。learner 不能把「沒看到」當成「沒發生」。

轉換器 cmd/eapconv：log 變成 captures

  • 一連線一 capture：transaction key 與 epoch 以 capture 為範圍，混在一起會混到 System Bytes。
  • 不丟東西：能解析的訊息成為 data 記錄（reconstructed）；加密、解不開或非訊息的內容成為帶原始 bytes 的註記。log 沒有連線事件，所以每筆都在 epoch 0、標 correlation-incomplete。
  • 版本：veq 釘在 tracepack v0.2.0（V-14，仍回報規格 2.28），轉換器先照 2.29／2.31 的規則做（V-16、V-19）。

在其中一個 EAP 版本上，stream 99 對象的訊息帶機台的 session ID，連線規則分不出來，會落在機台的 capture（eapsml-dialect §3）。

7. 分層的 prior 與 learners

好處：新機台資料少也能借用上層知識，差異也知道該歸哪層。pilot 兩台同型機共有的 93 個事件中 89 個連到相同 report（P1 §1），剩下的屬於 tool delta，不該污染機型層。

同一件事有好幾條規則時，聽誰的？（架構 §5）

  1. 只有 accepted、override 的規則生效；影響評分的 unresolved 擋住升版。
  2. Instance Overlay 最優先。
  3. 再來越具體越優先：tool delta → 機型 → vendor → 標準；下層牴觸上層就是 quirk，要有證據並被接受。
  4. 同層內：override → 已接受的 quirk → 手冊斷言 → library 預設。

learner 的共同介面（架構 §7）

輸入：一段證據＋目標層以上各層的 prior　→　輸出：某一層的片段，每條規則附來源、層級與信心值。

例如目錄由 cmd/logcat、手冊萃取與 ID 匯出檔學；模組內結構用被動自動機學習，以標準與手冊的狀態圖為 prior；交錯可用事件鍵控的模組選擇、物件狀態機的組合或插槽裡的序列模型。learner 可替換、在同一套 suite 上比較，外層迴圈才能挑；演算法留給 phase 3 與實作。

尚未對齊：架構 §6 不讓帶 correlation-incomplete 旗標的記錄成為 quirk 候選，但轉換後的 EAP log 每筆都帶這個旗標，而 G4-28（V-7 確認仍有效）允許 reconstructed 證據學語意層 quirk。三者怎麼搭配，規格還沒說。

8. 最難的部分：交錯

可行性原型用 6 小時那份 log 的前 4 小時學，預測其後 3,019 個事件的「下一個」（數字取自 P1 §1）：

模型猜中第一名平均 log-likelihood
整條事件流，看前兩個事件（全域 trigram）58%−1.73
看前面的事件決定下一個模組（事件鍵控）56%−1.68
參考：已知是哪個模組，只猜模組內的下一個77%—
  • 77% 與 58% 回答的是不同問題：它們支持「拆成模組狀態機」，但不是證明。
  • 只看上一個模組來選下一個模組，輸給全域 trigram；看前面的事件，log-likelihood 與前三名命中率最好，第一名略輸。
  • 這表示模組之間有可預測的相依，但分不出是同步轉移，還是 host 指令、製程階段這類共同原因。「物件狀態機能解釋交錯」是假設 H1，要有 report 定義的資料才能檢驗。

log-likelihood：模型給實際事件的機率取對數平均，越接近 0 越好（給 50% 是 −0.69，給 10% 是 −2.30）。

9. 評估與升版

  • 考題由 suite 固定，不由 candidate 決定；每個事件都要給大於 0 的機率，沒看過的 ID 走明確的未知事件額度。
  • 時序依 suite 定義的轉移類別評分，標明觀察位置：EAP log 的時間是 host 端時間。
  • 原有防護保留：凍結評分母體、第一個走錯就算失敗、coverage 不退步、negative control、絕對下限、scorecard 不加總。下限數值由 phase 2 定（架構裡的 95%／fixture 100% 是 V-4 之前的預設）。

證據切成三份

  • 考法：time-split、tool-split、type-split；宣稱「新機型也行」一定要 type-split。
  • 挑選用與確認用：挑選用的可反覆用；確認用的只確認已做好的選擇，每次使用都記帳、只回傳判定與 scorecard，誰都不能從中學。看過確認結果才提的方案要用全新資料再確認；額度用完只能換從未用過的證據。
  • 獨立單位：兩台機台的幾千個事件，仍只是兩次重複。

升版（架構 §9、§11）

  • 升版的是實際部署的組合（Profile、tool delta、runtime 載入的組合），每一個都不可修改、可重現。
  • gate 是確定性的：兩種分數都過下限；tool delta 在自己機台的 suite 上和「沒有 delta 的 Profile」比；上層變更會產生所有受影響 Profile 的新版本，都不能退步，且要人核准。
  • 來源階段不是擬真度：R 重播 → T 範本 → M 手冊推導 → C 校準 → S 學出結構 → G 假設，只說明規則從哪來；擬真度只能量出來。

10. 新機型上線與外層迴圈

  1. 只有手冊：產生 provisional Profile，只過不需要 log 的檢查，標為 manual-derived，不宣稱擬真度。
  2. 資料需求：依同類機型的 learning curve 估算還要多少 log，並建議開哪些錄製。絕不探測生產機台，只保留「維修時段、經人核准」的 hook。
  3. 資料到齊：重新學習，過完整 gate 才拿掉 provisional。

外層迴圈的目標：一次上線 episode 的成本

每次上線事先宣告成 episode：起點（手上的資料、各層 prior 的固定版本）、固定的目標、成本（兩個維度：證據的 tool-hours 與分類記錄的人時）。失敗的 episode 連同成本記錄，絕不丟掉。

比較方案（V-11）：先比成功率，不能降超過容忍度；再比兩邊都完成的 episode，兩個成本維度都不能變差超過容忍度、至少一個變好。其他情況交給人，不設權重。建共用資產（例如 vendor prior）是一次有預算、要核准的外層變更，效益只能在一整批 episode 上算總帳。

自主的範圍：服務只在已宣告的方案（learner、超參數、prior 權重）中自動選；新方案，包括 LLM 提的，先登錄為假設，人核准後才跑。人工審查也有預算。

事先登錄與判定規則

實驗在看到結果之前就把方案、cohort、證據、suite、指標與判定規則（含 margin δ）寫進 registry；資料庫拒絕沒有事先登錄或登錄晚於執行的結果。增益在每個獨立單位上量，取不確定區間和 δ 比：

初始假設（ve-generation-service §2.4）單位
H1物件狀態機比事件鍵控的模組選擇更能解釋交錯機型
H2機型 prior＋tool delta 勝過每台獨立學（likelihood 與回覆相符率分開判）機台
H3vendor 層 prior 讓新機型少收證據機型
H4手冊的行為斷言減少「沒看過的事件」的懲罰機型
H5LLM 提的假設值得人花時間審（每審查小時的經驗證發現數）審查批次

11. 資料與安全的界線

  • traffic log 不出 fab：學習只在本地 CPU 跑，每個 fab 一套服務；Profile 承接錄製資料的存取控制，也不出 fab。手冊可以送外部 LLM 萃取斷言。
  • LLM 只當顧問：打分與升版一律由確定性程式決定，外部模型的回覆只能當提案。不探測生產機台。
  • 兩個 registry 只增不改（V-12）：artifact 以內容雜湊命名存在 fab 的 MinIO，拒絕覆寫與刪除；紀錄存在 fab 的 MariaDB，服務帳號沒有 UPDATE／DELETE 權限。

從 log 衍生的內容送出 fab 時（V-11）

可以送出不能送出
彙總指標（scorecard、比率、次數、分位數）原始訊息與 SML 內容，片段也不行
結構，ID 換成每次放行重發的代號真實的 SVID／ECID／CEID／RPTID／ALID／RCMD 與名稱、單位
stream/function 與 SEMI 定義的代碼（HCACK、ALCD）變數值與範圍、recipe 名稱與內容
learner 與參數的描述機台、站點、lot、carrier、晶圓識別碼；絕對時間
至少 k 次、至少兩台機台的模式低於門檻的罕見模式

未分類的一律不送；新類別與範本由負責人指定的人核准；每次放行都記錄。k 由 phase 2 決定。

13. 名詞小辭典

EAP
Equipment Automation Program，工廠端控制機台的 host 程式。
gateway
介於機台與 EAP／FDC 之間的設備閘道，也可能自己回覆或發出訊息。
Profile
一種機型的行為說明書，有版本、不可修改。
tool delta
學出來的單台差異，獨立有版本。
Instance Overlay
操作員的站點設定，優先於學出來的規則。
capture／pack
tracepack 的一次錄製與組成它的檔案；轉換器每條連線一個 capture、每小時一個 segment pack。
vantage／fidelity
觀察位置，與每筆記錄的保真度。
prior
看資料前的合理預設，來自上層。
learner
負責學出 Profile 某一部分的可替換元件。
插槽（slot）
交錯選擇與值產生兩處，可放非狀態機元件。
quirk
不合標準、但真機確實如此的行為；VE 要重現它。
divergence
VE 與真機不一致之處。
suite／gate
凍結的考卷；升版門檻。
episode
一次事先宣告的新機型上線，用來量成本。
δ（margin）
事先定好「增益至少多大才採用」。
